1. Identificación y alcance

ITSANET IMS es una aplicación web para recepción y validación física de mercadería, registro de evidencias, trazabilidad por ítem, generación de informes y entrega de correo.

2. Arquitectura y comunicación

01 · AccesoPC / handheldNavegador · HTTPS · /app/
02 · EntradaApache2 · 8443Receptor del puerto publicado
03 · AplicaciónUvicorn · 3002FastAPI · reglas y API
04 · DatosMySQLSQLAlchemy + PyMySQL · transacciones

El navegador carga HTML, CSS y JavaScript bajo /app/. Las solicitudes de registro y consulta llegan al backend por la publicación HTTPS de Apache. Uvicorn ejecuta la aplicación ASGI de FastAPI; esta verifica sesión, permisos y reglas y utiliza SQLAlchemy/PyMySQL para persistir en MySQL.

Las directivas efectivas de proxy, el certificado y sus vencimientos se administran en Apache. La escucha local de un puerto no demuestra su accesibilidad desde Internet.

5. Modelo de datos e integridad

El modelo declara 30 tablas. Las tablas app_* conservan la operación web actual; las tablas iniciales de recepción coexisten para compatibilidad. operadores, sesiones y el maestro de productos son componentes compartidos. No eliminar tablas de compatibilidad sin revisar sus consumidores y migración.

app_recepciones.codigo
├── app_lineas             (packing original y orden)
├── app_skus               (estado agregado por SKU)
│   └── app_calidad_skus
├── app_eventos            (libro de registros y correcciones)
├── app_unidades_logisticas (bultos y cajas)
├── app_archivos
│   ├── app_archivo_identidades
│   ├── app_archivo_skus
│   ├── app_evidencias     (SKU, categoría y unidad)
│   └── app_copias_drive

operadores → sesiones y presencias
productos → producto_codigos
app_stock_depot: clave compuesta SKU + cliente
  • InnoDB y utf8mb4 definidos para las tablas MySQL; claves primarias, claves externas e índices según el modelo.
  • Cantidades: DECIMAL(14,3); precios: DECIMAL(14,4). SQLAlchemy devuelve estos valores a Python como float según la configuración declarada; deben conservarse las validaciones de suma y exportación.
  • Fechas: DATETIME con milisegundos en MySQL. La sesión SQL utiliza UTC; la presentación operativa usa America/Guayaquil.
  • Modo SQL estricto: STRICT_ALL_TABLES y NO_ENGINE_SUBSTITUTION. Pool con pre-ping; valores predeterminados: tamaño 5, overflow 5, reciclaje 3600 s.
  • El identificador del evento permite reconocer reintentos. Las correcciones conservan motivo y registro compensatorio; app_skus es una proyección recalculable de eventos.
  • Las relaciones CASCADE se documentan en el diccionario: una eliminación de cabecera puede afectar hijos. Las intervenciones directas en SQL requieren revisión y respaldo.

El árbol resume relaciones funcionales; el diccionario indica cuáles están declaradas como claves externas. La bitácora de aplicación no equivale a almacenamiento inmutable frente a un administrador de base de datos.

7. Ciclo de vida de las imágenes y evidencias

Los bytes del archivo se almacenan fuera de MySQL. La base conserva identidad, tamaño, SHA-256, autoría, clasificación, vínculos al registro y estado de copia. Una misma imagen puede justificar varios SKU mediante asociaciones y accesos directos, sin crear un archivo físico por cada vínculo.

PasoProcesamientoRegistro principal
1. CapturaCámara/galería; selección de recepción, embarque, SKU y categoría.Borrador del navegador cuando es posible.
2. GuardadoArchivo operativo y metadatos; vinculación con bulto/SKU/incidencia.app_archivos, app_evidencias y asociaciones.
3. ProgramaciónPersistencia de la carga pendiente y del destino.app_copias_drive.
4. TransferenciaOAuth; reserva de ID remoto; carga multipart; comparación MD5 remoto con contenido.Drive API + datos de la cola.
5. ConfirmaciónGuardar ID, enlace y destino comprobado. Conservar miniatura.drive_id / drive_url y estado COPIADA.
6. RecuperaciónReintento con identidad estable; errores de cuenta/permisos pasan a revisión.Intentos, próximo intento, error y monitor.

Estados de copia: PENDIENTE, PROCESANDO, COPIADA, REVISION y ELIMINADA. Una miniatura visible no confirma la copia a Drive. La aplicación comprueba además la ubicación vigente; mover o renombrar carpetas fuera del flujo puede producir una revisión del destino.

VAL_DATA_DIR/
├── app_archivos/ID_ARCHIVO     # contenido local retenido
├── app_miniaturas/ID_ARCHIVO   # vista previa
├── secretos/integraciones.key # clave de cifrado, acceso restringido
├── uploads/                   # archivos de entrada según flujo
├── exports/                   # salidas según flujo
└── fotos/                     # rutas de compatibilidad

Tras confirmar Drive puede liberarse el original local y conservarse su miniatura. La recuperación de evidencias requiere una política propia de Drive, además del respaldo del servidor. El archivo de configuración protegido y la clave de cifrado forman parte del respaldo seguro.

El árbol muestra rutas posibles, no carpetas creadas de forma anticipada. La preparación consulta las rutas existentes; la subida materializa únicamente la ruta utilizada. Si una carga falla después de crear su ruta, puede quedar una carpeta sin contenido; no existe una garantía transaccional entre MySQL y Drive ni una limpieza automática de todas las carpetas históricas.

  • Cliente y marca son segmentos opcionales. También puede reutilizarse una carpeta de recepción ya identificada y validada.
  • Si no hay embarques definidos, la categoría queda directamente bajo la recepción. Con embarques, la evidencia común puede quedar en COMPARTIDAS; la evidencia que requiere asignación puede quedar en POR-ASIGNAR.
  • Las rutas de SKU pueden incluir BULTOS/Bulto…/Caja… cuando existe vínculo con una unidad logística. OTRAS-EVIDENCIAS cubre los tipos sin categoría específica.
  • INFORMES se ubica directamente bajo la recepción en el servicio de Google Drive API.
  • Cuando una imagen documenta varios destinos, se crean accesos directos al archivo. No confundir un acceso directo con una copia independiente.
  • Se reservan IDs antes de subir, se reutilizan en reintentos y se rechazan rutas ambiguas con carpetas duplicadas. Los enlaces se guardan con su referencia de evidencia.

Ejemplo de vínculo: recepción → embarque → PNC → SKU → imagen. La evidencia identifica la condición PNC y el registro de cantidades identifica unidades/pallet/posición; el nombre de la carpeta no sustituye estos datos. No borrar carpetas vacías históricas sin contrastar referencias y accesos directos.

9. Autorización Google, correo y catálogo

Google central

El cliente OAuth web central se configura con su origen HTTPS y URI de retorno exactos. El flujo emplea PKCE S256 y estado de uso único. El código incluye el retorno /api/auth/google/callback; el valor registrado debe coincidir con la configuración efectiva. Los permisos operativos de Gmail/Drive se distinguen del acceso de usuario al aplicativo.

IntegraciónIdentidad y alcance
GmailCada remitente autoriza su propia cuenta; permisos gmail.readonly y gmail.send.
DriveCuenta operativa autorizada por ADMIN; permiso drive. El acceso de ejecutivos/clientes depende de los permisos reales de la carpeta.
CredencialesTokens cifrados con Fernet en app_config; clave externa integraciones.key. No se entregan al navegador.
RenovaciónEl backend renueva access tokens mediante refresh token. Revocación/cambio de cliente exige reconexión de la cuenta.
CompatibilidadApps Script se conserva como alternativa anterior; la vía central evita un despliegue individual por supervisor.

Documentos y correo

Los informes se versionan mediante huella y tipo. El usuario selecciona los adjuntos y sus nombres finales. La cola conserva la instantánea de entrega y su resultado. Un envío pendiente no es una confirmación: ante una respuesta interrumpida se consulta el estado y Enviados antes de repetir.

El informe al ejecutivo conserva la estructura original: PALLET/posición con identificadores limpios; el detalle de cantidades y PNC se agrega al final. El informe de auditoría puede incluir mayor desglose. Las cantidades se exportan como valores numéricos; las fotografías incluidas deben tener su vínculo verificado.

Depot y maestro

La API de catálogo/stock se utiliza si las credenciales están habilitadas; existe maestro local y caché. Los archivos CSV/XLSX sirven al flujo operativo de carga y revisión. La integración documentada no implica escritura automática de mercancía en Depot.

  • Roles de aplicación: OPERADOR, SUPERVISOR y ADMIN; las autorizaciones se validan en el servidor. ADMIN funcional no equivale a root del sistema operativo.
  • La credencial local se conserva como hash PBKDF2-HMAC-SHA256 con sal. La sesión utiliza token aleatorio y cookie HttpOnly / SameSite=Lax.
  • La clave externa de integraciones se protege con permisos restringidos. Su pérdida impide recuperar las credenciales cifradas existentes.
  • La actualización de vistas combina SSE por recepción con consulta alternativa de 4 segundos. El proxy debe permitir conexiones continuas.
  • La presencia informa quién trabaja sobre el SKU; no sustituye los controles de concurrencia e idempotencia. Preservar borradores al actualizar vistas.
  • La política institucional define exposición de red, accesos, retención y renovaciones. Los controles descritos no constituyen certificación normativa ni garantía de alta disponibilidad.

11. Calendario de mantenimiento

Las siguientes frecuencias constituyen el plan preventivo recomendado. Su ejecución debe registrarse con fecha, responsable, resultado y acciones pendientes. La programación automática y la retención se verifican en el servidor antes de considerarlas implantadas.

FrecuenciaActividadResponsable funcional
Diaria / inicio de jornadaAcceso, pendientes de fotos/correos, errores, catálogo y disponibilidad.Administrador funcional / supervisor.
DiariaVerificar respaldo SQL, archivos, clave y configuración; comprobar resultado e integridad.Administrador de infraestructura.
SemanalCapacidad de disco/RAM, crecimiento, colas, errores recurrentes y registros del servicio.Infraestructura + mantenedor.
MensualUsuarios/roles, cuentas sin uso, permisos Drive, dependencias y vencimiento de certificado.Infraestructura + mantenedor + ADMIN.
TrimestralEnsayo de restauración aislada y revisión de capacidad y continuidad.Infraestructura + mantenedor.
Antes y después de cada cambioPruebas, respaldo, revisión Git, aplicación controlada y verificación funcional.Mantenedor + infraestructura + supervisor.

Actualización del aplicativo

  • Reproducir y corregir en un entorno separado; verificar cantidades, reportes, fotos y permisos afectados. No ejecutar pruebas contra producción.
  • Registrar commit completo y ventana del cambio. Usar scripts/actualizar_produccion.sh según su procedimiento; no reinstalar el servicio desde la plantilla servicio.sh.
  • El actualizador prepara dependencias antes de la parada y respalda datos/configuración; luego reinicia la aplicación y verifica respuesta.
  • Comprobar acceso, una operación representativa, informes y las integraciones que cambien. Conservar borradores/fotos pendientes del navegador.
  • Documentar resultado y recuperación prevista. Volver al código anterior no restaura la base de datos.

No actualizar dependencias directamente a la última versión en producción. La evolución V2 se desarrolla aparte de la línea estable: incorporación gradual de otros clientes, revisión de claves SKU, permisos, catálogos, formatos y separación de evidencias antes de cada piloto.

Recomendación: respaldo diario y antes de cada cambio, con copia fuera del servidor y ensayo trimestral. La institución define retención, RPO (pérdida tolerable) y RTO (tiempo de recuperación). El respaldo previo al pase incluido en el código no acredita por sí solo un respaldo diario programado.

  • Distinguir red/DNS, Apache, Uvicorn, MySQL y proveedor externo mediante consultas de diagnóstico.

  • Ante fotos pendientes, conservar el original y reintentar con la identidad registrada. Ante correo pendiente, verificar confirmación y Enviados.
  • Restaurar primero en un entorno aislado; validar cantidades, usuarios, archivos y lectura de evidencias. Coordinar cualquier recuperación productiva y su impacto.
