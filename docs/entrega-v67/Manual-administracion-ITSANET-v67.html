2. Usuarios, roles y configuración

  1. ADMIN entra a Administración y Usuarios. Revisar nombre, correo, estado activo, rol y permisos; evitar cuentas compartidas.
  2. Aprobar las solicitudes que corresponden y asignar los permisos necesarios. Verificar que un operario puede contar pero no configurar integraciones ni enviar desde otro buzón.
  3. Mantener correo exacto del supervisor en su ficha: OAuth exige coincidencia con Google. Corregir una ficha no concede autorización para operar como otra persona.
  4. Desactivar las cuentas al retirar acceso. Revisar también autorizaciones Google y propiedad del repositorio cuando cambia el responsable.
  5. Revisar clientes, marcas, repositorios y formatos de importación/exportación. Probar los cambios con una recepción de prueba antes de usarlos en el turno.
No ejecutar el instalador inicial ni recrear el archivo de entorno para actualizar una instalación que funciona. El procedimiento de actualización preserva los datos y conexiones existentes.

3. Configurar Google central una vez

  1. TI crea o utiliza el proyecto corporativo de Google Cloud, habilita Google Drive API y Gmail API y conserva su propiedad institucional.
  2. Configura audiencia y pantalla de consentimiento. Verificar si participan cuentas externas Gmail; una audiencia solo interna no las admite. Revisar políticas Workspace y verificación de permisos aplicables.
  3. Crea cliente OAuth de tipo Aplicación web y registra la URI exacta de callback: para el origen informado, https://apps.flexnetuio.com:8443/api/auth/google/callback. Debe coincidir con HTTPS, hostname, puerto y ruta reales.
  4. ADMIN abre Administración → Conexiones → Google central; guarda Client ID, Client secret y callback. El secreto se configura de forma privada, no se envía por correo ni se incluye en capturas.
  5. ADMIN autoriza su cuenta operativa de Drive y la selecciona para almacenamiento. Verifica carpeta raíz o repositorios por cliente/marca y acceso a los archivos existentes.
  6. Cada supervisor abre Mi cuenta → Conectar con Google y autoriza el mismo correo de su ficha. Comprobar Gmail. No crea su propia aplicación web Apps Script.
  7. En una recepción de prueba, guardar foto, comprobar confirmación/enlace, descargar informe y revisar un envío autorizado al destinatario de pruebas. Registrar acuse y permisos de acceso a las fotos.

Apps Script queda como compatibilidad para instalaciones que aún lo requieren o exportación opcional a Sheets. V67 evita llamar a un preparador masivo antiguo; para la vía central basta actualizar el servidor. No es obligatorio republicar una app web por cada supervisor.

4. Supervisión diaria y capacidad

  • Al iniciar la jornada, revisar Avisos y constancia de actualización masiva de catálogo por cliente. Consultar un solo SKU no acredita actualización completa.
  • Revisar Procesos y errores como ADMIN: estado actual, intentos, referencia y causa. Filtrar por recepción y exportar diagnóstico JSON cuando se solicite soporte.
  • Controlar fotos guardadas frente a confirmadas, pendientes de asignar embarque, carpetas desactualizadas y entregas en REVISION.
  • No confundir CANCELADA con fallo: puede ser una acción deliberada. Confirmar el último envío vigente y los documentos asociados.
  • Medir disco disponible, almacenamiento local pendiente, datos/índices SQL, memoria/carga y duración de reintentos. Comparar capturas entre jornadas; un valor puntual no demuestra tendencia.
  • Revisar permisos y retención Drive y cuota de correo. Un respaldo de MySQL no reemplaza la recuperación de originales que ya solo están en Google.

5. Diagnóstico de solo lectura

Estos comandos muestran revisión, estado y salud local. No prueban por sí solos una recepción completa ni un envío:

cd ~/bryan/IV_ITSANET
git rev-parse HEAD
systemctl is-active iv-itsanet
curl --fail --silent http://127.0.0.1:3002/health
sudo journalctl -u iv-itsanet -n 80 --no-pager

Para registrar infraestructura, configuración sin valores secretos, puertos, TLS, capacidad y estado SQL, usar la captura acotada de lectura. Escribe únicamente informes privados fuera del código; no reinicia, migra ni actualiza MySQL:

cd ~/bryan/IV_ITSANET
sudo systemd-run --quiet --wait --pipe --collect \
  --unit="iv-auditoria-$(date +%s)" --uid="$(id -un)" \
  --property="WorkingDirectory=$PWD" \
  --property=EnvironmentFile=/etc/iv-itsanet.env \
  "$PWD/.venv/bin/python" "$PWD/scripts/auditar_servidor_lectura.py" \
  --repo "$PWD" --salida "$HOME/bryan/auditorias-itsanet"
Revisar los diagnósticos antes de compartirlos: pueden contener nombres de rutas, referencias operativas y metadatos. El helper no imprime contraseñas ni claves; no adjuntar archivos .env ni la clave privada.

6. Actualizar producción

  1. Leer el manifiesto y el comando exacto de la entrega. Identificar commit completo, rama operativa y versión de interfaz; no usar reset --hard para eludir cambios locales.
  2. Avisar una pausa de registros; confirmar con el equipo los guardados pendientes. Ejecutar el comando publicado que extrae scripts/actualizar_produccion.sh del commit probado.
  3. El actualizador comprueba servicio, ruta, avance de Git, dependencias y herramientas de respaldo. Prepara dependencias, detiene solo iv-itsanet, respalda base y datos y aplica la versión.
  4. Esperar resultado y registrar ruta de respaldo. Si falla, conservar el diagnóstico y comprobar recuperación del código anterior antes de retomar el trabajo.
  5. Recargar PC y handheld. Comprobar una recepción existente, fecha/filtros, lectura de etiquetas, datos y enlaces; las nuevas categorías solo aparecen al copiar archivos.
  6. Registrar commit, hora, resultado, persona ejecutora y aceptación funcional. Un mensaje del chat o una rama publicada no certifican que el pase se haya ejecutado.
El comando con el hash exacto se incluye en la entrega final. Se utiliza el servicio y la base existentes; no se importan volúmenes ni usuarios de desarrollo.

7. Respaldar y recuperar

ElementoQué debe conservarse
MySQLDump consistente, checksum y revisión del código correspondiente. Incluye datos operativos y referencias; no incluye por sí mismo los bytes originales en Drive.
Archivos privadosVAL_DATA_DIR, evidencias pendientes, informes locales, miniaturas y secretos/integraciones.key con permisos correctos.
Configuración/etc/iv-itsanet.env, unidad de systemd y configuración de proxy/certificado bajo custodia TI. El actualizador copia el entorno en su respaldo privado; no presume un respaldo completo de Apache o TLS.
GooglePropiedad y acceso del repositorio, política de retención/recuperación, autorizaciones y continuidad de la cuenta operativa.
Código / dependenciasCommit, requisitos y artefactos disponibles. Volver a un commit no restaura filas SQL ni garantiza revertir dependencias ya instaladas.
  1. Ensayar la restauración en otra base y ruta, con conexiones de correo/Google deshabilitadas para evitar envíos reales.
  2. Restaurar el SQL y los archivos del mismo punto de respaldo; recuperar la clave privada que descifra las credenciales sin publicarla.
  3. Arrancar el código compatible y validar relaciones, cantidades, eventos/anulaciones, descarga, evidencia y acceso. Revisar las colas sin reanudar entregas automáticamente en el ensayo.
  4. Medir el tiempo de recuperación y documentar la pérdida de datos tolerable. Solo después aprobar un procedimiento productivo y una ventana de sustitución con TI.
No se aporta un comando destructivo de restauración genérico. El servidor comparte servicios y los destinos reales deben identificarse antes de reemplazar una base o carpeta. Un respaldo debe probarse, no solo existir.

8. Resolver incidencias sin duplicar datos

CasoAcción operativa / TI
Foto guardada, Drive pendienteConservar el original. Revisar causa en monitor, cuenta operativa, permiso, cuota y conexión; reintentar desde la recepción manteniendo ID.
Hay categorías vacías antiguasV67 detiene la precreación. Revisar contenido, subcarpetas y enlaces históricos antes de cualquier limpieza autorizada. No borrar por nombre ni interpretar ausencia de fotos como cantidad física cero.
Carpeta duplicada o movidaRevisar IDs y ruta; el sistema no elige arbitrariamente carpetas duplicadas. Conservar referencias de las entregas anteriores.
Correo sin acuseRevisar Enviados del remitente propio, referencia e hilo. Utilizar la recuperación controlada; no pulsar Enviar repetidamente.
Datos no se refrescanComprobar misma recepción/versión, sesión, red y SSE en el proxy. La consulta de respaldo funciona cada cuatro segundos; no desactivar controles de concurrencia.
No se guardó corrección de bultosLeer el rechazo: fotos/códigos/registros, reserva de impresión o cambio de total concurrente. No borrar bultos utilizados para forzar consolidación.
Excel solicita reparaciónGuardar el archivo original y el registro de reparación XML, junto con formato/revisión. No sustituir cantidades por texto ni eliminar información hasta identificar el elemento.
No abre la cámara en handheldComprobar HTTPS/origen, cadena del certificado, permiso y navegador. Evitar HTTP por IP como solución. Comprobar el lector físico por separado.
Clave privada inaccesibleRestituir desde respaldo seguro con permisos correctos; no generar otra clave para intentar descifrar credenciales anteriores.
Servidor o DB no respondeConservar diagnóstico y revisar servicio, conexión/pool, espacio y recursos. No recrear tablas ni correr fixtures de pruebas en producción.

Para escalar: registrar versión, recepción/archivo/SKU, hora de Ecuador, acción y mensaje. Adjuntar diagnóstico sanitizado y revisión del informe. Contraseñas, tokens, claves y contenido privado de buzón quedan fuera del ticket.
