TEMA 2

Servidor empresarial y archivos privados

  • Repositorio: ~/bryan/IV_ITSANET.
  • Servicio systemd: iv-itsanet, puerto 3002.
  • Variables privadas: /etc/iv-itsanet.env, cargadas por systemd. No cambiarlas de permisos ni copiarlas a pruebas.
  • VAL_DATABASE_URL: MySQL empresarial; VAL_DATA_DIR: archivos y clave de cifrado propios.
  • La clave de cifrado de integraciones se conserva con los datos. Un campo secreto vacío conserva su valor guardado.

El actualizador hace respaldo verificable de base, archivos y configuración; pausa el servicio durante el pase y comprueba salud e interfaz. No usar reset/clean ni importar una base de desarrollo sobre producción.

TEMA 3

Estructura del código

  • app/main.py: arranque, rutas y trabajadores.
  • app/routers/: API, permisos, sesión, recepción, archivos e integraciones.
  • app/services/app_modelo.py: recepción, conteo, anulación y cierre.
  • entregas.py, correo_redactado.py, historial_entregas.py: instantáneas, correo, cola y declaración manual.
  • informes.py, drive.py: documentos archivados, enlaces y copia de fotos.
  • firebase/public/: interfaz compartida; módulos ESM con versión común y caché controlada.
  • apps-script/: Proxy.gs, Servidor.gs y contratos Google.
  • scripts/, docker/, compose*.yaml: instalación, respaldo, impresión y entornos aislados.
  • tests/ y firebase/test/: pruebas de API, MySQL, concurrencia e interfaz.
TEMA 4

Concurrencia y protección de estados

Las escrituras operativas bloquean la recepción y las filas correspondientes en MySQL. Los conteos tienen identificadores idempotentes; las correcciones se registran como movimientos auditados. El cierre valida la lista de eventos y la huella del informe. Un informe pertenece a una recepción y a su autor.

La versión del correo se vincula al usuario, a la fuente de datos y a la revisión del borrador. Un cierre repetido debe corresponder a la misma solicitud. Los cambios de gestión de entregas requieren una versión actual y una razón. PROCESANDO no se cancela ni se declara manualmente durante la operación.

La autorización de Google es por remitente real, con HMAC cifrado y cuenta ejecutora comprobada. Las llamadas externas no conceden permiso para enviar desde otra cuenta.

TEMA 5

HTTPS y acceso desde otra red

El supervisor de casa necesita una URL HTTPS alcanzable y su cuenta; no necesita SSH ni estar en la LAN. La instancia de pruebas puede publicar un enlace temporal mediante un túnel saliente. No se abren MySQL ni puertos de administración.

Producción sigue en 3002. Las pruebas usan contenedores, volúmenes, archivos y claves diferentes, con puerto local 3003. Un enlace temporal no es un dominio empresarial permanente y depende del proceso de túnel.

Para HTTPS permanente, TI debe asignar un dominio y un proxy inverso que dirija /app/ y /api/ al mismo servicio, con certificado confiable. No conectar un frontend HTTPS a una API privada HTTP desde el navegador. Ver la guía de publicación incluida en docs.

TEMA 6

Qué se puede probar en Firebase

Hosting sirve archivos estáticos. La versión MySQL necesita también FastAPI alcanzable por HTTPS y autenticación coherente. Una publicación de Hosting en la raíz activa la ruta histórica hacia Firestore; no reproduce los flujos nuevos exclusivos de /api/operacion.

Conservar la web existente. Para experimentar, usar un canal de vista previa y un backend/ambiente de pruebas explícito, o el enlace HTTPS de la instancia completa. No ejecutar firebase init sobre la configuración existente ni desplegar reglas o Functions de producción por probar una interfaz.

TEMA 7

Conexiones Google y Depot

  1. ADMIN registra conexiones Depot por cliente; la actualización del catálogo usa esas APIs.
  2. Cada supervisor tiene su Apps Script con Proxy.gs, Clientes.gs y Servidor.gs compatibles, la carpeta autorizada y SERVIDOR_HMAC.
  3. El propietario autoriza Google una vez y publica la aplicación web como Ejecutar como Yo.
  4. ADMIN o el propietario guarda /exec y la misma clave en su ficha. La verificación debe confirmar su correo y acceso a Drive.
  5. Un despliegue de Git en el servidor no publica Apps Script. Actualizar ambos archivos del puente y una nueva versión del mismo /exec cuando cambie su contrato.

No registrar contraseñas Gmail en ITSANET. Mantener destinatarios, carpetas y credenciales de prueba separados.

TEMA 8

Diagnóstico y recuperación

sudo systemctl status iv-itsanet --no-pager
curl -fsS http://127.0.0.1:3002/health
sudo journalctl -u iv-itsanet -n 80 --no-pager

Salud y acceso comprueban el servicio, no confirman un correo ni una impresión física. Para Google revisar una entrega real y su acuse; para Zebra imprimir una etiqueta y leerla.

Si falla un pase, el actualizador conserva el respaldo y trata de arrancar el código anterior. Revisar sus diagnósticos antes de restaurar datos. No ejecutar pytest contra la base empresarial: sus fixtures de prueba pueden recrear tablas.
